# mediahead

Good writing doesn't tell people what I built. It shows them why I built it.

Every piece leaves the reader with one **realization** — how I think — not a list of achievements. Projects, tech, and results are supporting cast. The realization is the main character.

## Steps

### 1. Find the realization

Answer one question: **"What did I realize?"** — one sentence, a shift in thinking, not a feature.

The realization must come from the user. If the input is only a project, README, or changelog, ask the user what surprised them, what they got wrong first, or what they'd tell a peer over coffee. Draft only after they answer.

Done when: one sentence states the realization in the user's own terms.

### 2. Pick the spine

Write the one line that stands alone — the sentence people remember after forgetting everything else. Usually the realization, sharpened.

- *A portfolio shouldn't tell people what you've built. It should show them how you think.*
- *More dashboards don't create better decisions.*

Everything else in the piece supports this line.

### 3. Pick the hook

Open with an **observation**: something the reader has experienced but never put into words. The announcement comes later, if at all.

Good sources: a surprising observation, a common misconception, a tradeoff, a mistake, the moment thinking changed.

- *Most portfolios ask you to scroll.*
- *Most AI projects don't fail because of the model.*
- *The hardest part wasn't building it. It was deciding what to leave out.*

### 4. Draft along the idea flow

```
Observation → Context → Problem → Realization → Solution → Reflection → Conversation starter
```

One beat per short paragraph. Each paragraph reveals something new; move forward through ideas, not through a timeline.

Apply the reference rules below while drafting.

### 5. End with an open question

Leave the idea, then invite perspective with a question that has many valid answers.

- Good: *What makes a technical portfolio worth exploring?* / *How have you handled this tradeoff?*
- Weak: *Thoughts?* / *Agree?* — these ask for engagement, not perspective.

### 6. Run the litmus test

Every answer must be yes:

- Does it sound like someone thinking out loud?
- Does it teach something, beyond announcing something?
- Did the story earn every technology it mentions?
- Is there one line people will remember?
- Would it still be interesting with every technology name removed?

Any no → rewrite that part and re-run. Done when all five are yes. Then hand the user the draft plus the spine line and realization called out separately, so they can check both are true to them.

## Reference rules

**Reveal, don't claim.** Readers discover expertise; the piece never announces it.

| Instead of | Write |
|---|---|
| *I built an AI-powered platform.* | *I wanted to see whether AI could simplify this workflow.* |
| *I have experience with RAG, MCP, Docker…* | *While building a RAG pipeline…* / *When experimenting with MCP…* |

Technology appears only where the story needs it to solve a problem — never as a list.

**Voice.** An experienced engineer talking to peers over coffee after solving an interesting problem. Curious before authoritative, reflective before celebratory, technical without going academic, practical over theoretical.

**Emotion.** Understated. *I realized… / Building this reminded me… / That small decision changed how I approach…* Confidence comes from clarity, not adjectives. Launch-speak (*thrilled, excited to announce, game-changer, this changed everything*) gets cut on sight.

**Keep a sentence only if it** teaches, surprises, explains, advances the story, or creates curiosity. Everything else — repetition, buzzwords, over-explaining, decoration — goes.

**Language.** Short paragraphs, one idea each, plenty of whitespace. Active voice, simple words, medium sentences. Specific over abstract, concrete over clever.

**Shape.** 250–500 words. 5–8 short paragraphs, one per flow beat (no headers unless the platform is a blog). Roughly: mostly insight, some story, a small actionable takeaway; conversational first, technical second.

## Final rule

Write so readers remember the idea, not the achievement. If they remember how you think, they'll remember what you built.
